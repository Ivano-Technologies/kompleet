# IVA-322: Convex Auth 2.0 migration assessment

- Date: 13 November 2026
- Scope: assessment only. No migration, no dependency upgrades, no code changes.
- Apps read: Kompleet (`dev` at `008faab`) and Ivano PMS (`dev` at `6b013c2`, read only).
- Auth 2.0 sources: official Convex docs, the Convex launch post, the GitHub release and the npm registry, all read on 13 November 2026. Every Auth 2.0 claim below links to its source. Section 7 lists what could not be confirmed.

## Summary

1. **Do not migrate either app yet.** Convex's own migration guide says v2 "has fewer features than Convex Auth v1" at launch and that "Migration tooling will be available soon" ([migration guide](https://docs.convex.dev/auth/convex-auth/migrating/from-convex-auth-v1)). There are no documented migration steps today.
2. **Kompleet can migrate later, with real work.** Its email and password sign-in exists in v2, but v2 verifies by emailed link where Kompleet uses emailed codes, and the mobile app has no documented path.
3. **Ivano PMS cannot migrate as it stands.** PMS signs in with Google plus an emailed one-time code. v2 has "no magic links or one-time codes by email" ([launch post](https://stack.convex.dev/convex-auth-v2)).
4. **Nothing forces a move.** v1 "is still getting security updates for now" ([launch post](https://stack.convex.dev/convex-auth-v2)); no end date is given.
5. **Google sign-in for Kompleet: recommend staying email and password only.** Reasons in section 6.

## 2. What Auth 2.0 changes

Version 2.0.0 was published on 12 November 2026 ([GitHub release](https://github.com/convex/convex-auth/releases/tag/v2.0.0), which carries no release notes) and is the `latest` tag on npm (`npm view @convex-dev/auth dist-tags`, read 13 November 2026).

| Change | Detail | Source |
| --- | --- | --- |
| Rebuilt, not upgraded | Built from the ground up on Convex components. It "does not attempt to wrap or depend on any other third-party auth library", so `@auth/core` is no longer involved. | [Migration guide](https://docs.convex.dev/auth/convex-auth/migrating/from-convex-auth-v1) |
| Fewer features than v1 | "At launch, it actually has fewer features than Convex Auth v1, so some applications may not be able to migrate right away." | [Migration guide](https://docs.convex.dev/auth/convex-auth/migrating/from-convex-auth-v1) |
| Sign-in methods | Username and password, email and password, username and passkey, OAuth with Apple, Google and GitHub only. Other OAuth providers are "coming soon". | [Overview](https://docs.convex.dev/auth/convex-auth), [OAuth](https://docs.convex.dev/auth/convex-auth/methods/oauth) |
| Missing | No multi-factor authentication. No magic links or emailed one-time codes. React and Next.js only. | [Launch post](https://stack.convex.dev/convex-auth-v2) |
| Email verification | Built in, by validation link. The link "works only in the browser (or app) that started the flow". Password reset is also by link. Change password and change email are built in and send security notices. | [Email + password](https://docs.convex.dev/auth/convex-auth/methods/email-password) |
| Email sending | Sent through the `@convex-dev/resend` component, which is a peer dependency. | [Email + password](https://docs.convex.dev/auth/convex-auth/methods/email-password) |
| Rate limits | Built in and fixed: 5 emails per address, 20 emails per IP, 60 account lookups per IP, 5 password attempts per user, each refilling over time. "These values aren't configurable yet." | [Email + password, Rate limits](https://docs.convex.dev/auth/convex-auth/methods/email-password#rate-limits) |
| Passkeys | Username plus passkey, with list, add and remove. Email plus passkey is "coming soon". No bundled React Native passkey support yet. | [Username + passkey](https://docs.convex.dev/auth/convex-auth/methods/username-passkey) |
| No signing keys | "Your deployment signs the access tokens with its own key, thus you do not have secrets to configure." `JWT_PRIVATE_KEY` and `JWKS` are no longer needed. | [Getting started](https://docs.convex.dev/auth/convex-auth/getting-started) |
| Data location | Auth data lives in component tables, not in app tables. The app keeps its own `users` table and supplies a `createUser` mutation. Password hashes sit in the password component and app code cannot read them. | [Best practices](https://docs.convex.dev/auth/convex-auth/best-practices), [Launch post](https://stack.convex.dev/convex-auth-v2) |
| OAuth callback | The callback lives on the deployment's `convex.site` host, for example `/oauth/google/callback`. The return address is set by `allowedRedirectOrigins`. Google credentials are declared in `convex/convex.config.ts`. | [OAuth](https://docs.convex.dev/auth/convex-auth/methods/oauth) |
| Next.js wiring | New route handlers at `/auth/signin`, `/auth/refresh` and `/auth/signout`, a `signIn` allow-list of functions, and a new proxy built by `convexAuthNextjsProxy`. The refresh token is kept in an `httpOnly` cookie. | [Setting up Next.js](https://docs.convex.dev/auth/convex-auth/ssr-nextjs/setup) |
| Sessions | Sessions are reactive: signing out in one tab signs out the others. Change password offers "Sign out of all other devices". | [Launch post](https://stack.convex.dev/convex-auth-v2), [Email + password](https://docs.convex.dev/auth/convex-auth/methods/email-password) |
| Cost | Free and open source, no per-user billing. Normal Convex hosting usage still applies. | [Overview](https://docs.convex.dev/auth/convex-auth), [Launch post](https://stack.convex.dev/convex-auth-v2) |
| Requirements | Peer dependencies: `convex ^1.48.0`, `next ^16.0.0`, `react ^18 or ^19`, `@convex-dev/resend ^0.2.8`. | npm registry (`npm view @convex-dev/auth@2.0.0 peerDependencies`) |
| v1 support | v1 gets security updates "for now" while v2 closes the feature gaps. No end date. | [Overview](https://docs.convex.dev/auth/convex-auth), [Launch post](https://stack.convex.dev/convex-auth-v2) |

## 3. Effort per app

The day counts are my estimates from reading the code. They are not measured and assume Convex ships the promised migration tooling first.

### Kompleet: large, about 8 to 12 working days plus QA

| Work | Why |
| --- | --- |
| Rewrite `convex/auth.ts` on `setupEmailPassword` | The custom `authorize` wrapper has no direct equivalent. Legacy account trust, send limits and typed errors each need a new home or can be retired. |
| Replace code entry with link flows | Sign-up verification and password reset change from typing a code to opening a link. Login, sign-up, reset and the landing hero card all change, with new copy and new pages for the link targets. This is user-visible and needs Coco's Accept. |
| Move email sending to `@convex-dev/resend` | Replaces `convex/lib/authEmail.ts`. The custom send limits in `convex/authResend.ts` overlap with v2's fixed limits and should be removed or reconciled. |
| Rework account erasure | `convex/lib/eraseAccount.ts` deletes rows from five v1 auth tables directly. Under v2 that data is inside components. The erasure path must be rebuilt and retested, because it backs data deletion requests. |
| Schema | Drop the `...authTables` spread and decide what happens to the v1 auth fields on `users`. |
| Next.js wiring | Replace `src/proxy.ts`, the hand-written `/api/auth` handler and its helpers with the v2 routes and proxy. Check the new `/auth/*` routes against the existing `src/app/auth/callback/route.ts`. |
| Mobile app | The Expo app signs in by posting a v1 action to `/api/auth`. v2 documents React and Next.js only, so this needs a design decision before any estimate holds. |
| Dependencies and keys | `convex` must rise from `^1.46.0` to at least `^1.48.0`. `@auth/core` can be removed. `JWT_PRIVATE_KEY` and `JWKS` are retired and new variables are declared for Resend. These are environment changes that need Kezie's OK. |
| Tests | Auth has wide test cover (`convex/lib/auth*.test.ts`, `src/lib/auth/*.test.ts`, `src/__tests__`, the e2e OTP hook). Most of it must be rewritten. |
| Data migration | Moving existing accounts into the components. No tooling or documented method exists yet. |

### Ivano PMS: blocked today

PMS's second sign-in method is an emailed one-time code, which v2 does not have. PMS can only move if one of these happens:

1. Convex adds emailed codes to v2 (the launch post says more features are on the way, with no date).
2. PMS replaces the emailed code with email and password, which is a product decision.
3. PMS goes Google only, which locks out anyone who signs in by code today.

If one of those is settled, the code change is medium, about 4 to 6 working days: PMS has far less custom auth code than Kompleet, and its Google sign-in maps onto `setupGoogle`. The Google redirect address changes, so the Google Cloud OAuth client must be updated at cutover.

## 4. Risks

| Risk | Severity | Note |
| --- | --- | --- |
| No migration tooling or documented steps | High | Any migration today is hand-built against undocumented component tables. |
| Existing passwords may not carry over | High | See section 5. Worst case is every user resetting their password. |
| Everyone signed out at cutover | Medium | See section 5. Plan for it. |
| Link that only works in the starting browser | Medium | A user who signs up on a laptop and opens the email on a phone cannot finish there. Kompleet's current codes do not have this limit. |
| Mobile app sign-in breaks | High for mobile | No documented v2 path for the Expo client. |
| Account erasure regresses | High | The erasure code touches v1 tables by name. A missed table leaves personal data behind. |
| Fixed rate limits | Low | Not configurable yet. 5 password attempts per user, then one per minute. |
| Version 2.0.0 is one day old | Medium | The release has no notes, and the docs still point at a `reboot` branch for examples. Early fixes are likely. |
| PMS feature gap | Blocker | No emailed codes in v2. |
| Staying on v1 | Low for now | Security updates continue with no stated end date. Watch for an end-of-support notice. |

## 5. Impact on existing users and sessions

**Forced sign-out: plan for yes.** The official guide does not say. v2 signs tokens with the deployment's own key instead of `JWT_PRIVATE_KEY` ([Getting started](https://docs.convex.dev/auth/convex-auth/getting-started)) and keeps sessions in component tables, so I expect v1 sessions to stop working at cutover. This is my inference, not a documented fact. A third-party upgrade note for a 2.0 beta reports that the session tables had to be cleared, signing every user out ([natedunn/kino pull request 181](https://github.com/natedunn/kino/pull/181)); that is a secondary source and I read it only through search results.

**Password hashes: unconfirmed, and the biggest open question.** v1 hashes passwords with Scrypt by default ([v1 Password provider reference](https://labs.convex.dev/auth/api_reference/providers/Password)); Kompleet does not override it. In v2 the hashes sit inside the password component and app code can only set or check a password ([launch post](https://stack.convex.dev/convex-auth-v2)). I found no documented way to import existing hashes. If the coming tooling does not cover this, every Kompleet user would have to reset their password. PMS has no passwords, so this does not apply there.

**Verified email status: unconfirmed.** Kompleet records verification on `authAccounts` and `users`, with a special rule that trusts accounts older than the verification cutoff. v2 treats its email component as the source of truth for verified email ([Best practices](https://docs.convex.dev/auth/convex-auth/best-practices)). Whether existing verified status can be carried over is not documented.

**Account linking: unconfirmed, likely not automatic.** In v2 each provider is its own component and the OAuth guide says a `users` row is created for each account ([OAuth](https://docs.convex.dev/auth/convex-auth/methods/oauth)). I found no documented linking of a Google account to an existing email and password account with the same address. A tester's issue on the Convex repo says v1 OAuth accounts are not carried over automatically ([convex/convex-auth issue 796](https://github.com/convex/convex-auth/issues/796)); also a secondary source read through search results. For PMS this matters directly: existing Google users must map to their current `users` rows or they lose their data link.

**User records and app data: not affected.** Both apps keep their own `users` table, which v2 continues to use ([Best practices](https://docs.convex.dev/auth/convex-auth/best-practices)). A different table name is also supported ([Existing user data](https://docs.convex.dev/auth/convex-auth/migrating/existing-user-data)).

## 6. Recommendation: Google sign-in for Kompleet

**Stay email and password only.** Do not turn on Google sign-in as part of an Auth 2.0 move.

1. **Product and legal pages already agree.** Kompleet offers password sign-in only, the Google OAuth wording was removed from the legal pages in pull request 209 (`7f385a6`), and the IVA-224 drafts remove the same claim. Staying as is needs no further legal change.
2. **Google sign-in is not a 2.0 feature.** v1 supports it too; PMS uses it today. Auth 2.0 gives no new reason to add it.
3. **It would reopen the Privacy Policy.** Google would become a recipient of sign-in data and a source of profile data. The policy would need to say so, and the drafts still await a Nigerian lawyer's review under IVA-224. Adding Google now means a second round of drafting and review.
4. **Duplicate accounts are a real risk.** With no documented account linking in v2 (section 5), a user who signed up with a password and later clicks "Sign in with Google" could get a second, empty account. For a bookkeeping product that looks like lost data.
5. **It adds cutover work.** A Google Cloud OAuth client, a consent screen, a redirect address on the Convex site host, and two new secrets.

If Google sign-in is wanted later, raise it as its own ticket after the migration has settled. That ticket should ship the product change and the Privacy Policy wording together, and should first confirm how v2 handles a Google sign-in for an address that already has a password account.

### Suggested next steps

1. Leave both apps on v1. No action needed now.
2. Recheck the [migration guide](https://docs.convex.dev/auth/convex-auth/migrating/from-convex-auth-v1) when Convex publishes the tooling. The three things to look for: password hash import, session handling at cutover, and account linking.
3. Before committing Kompleet, decide what the mobile app does.
4. Before committing PMS, decide what replaces the emailed code, or wait for v2 to add it.
5. When the time comes, trial the migration on a dev deployment with a copy of a few real accounts before any production plan.

## 7. What I could not confirm

- **How to migrate at all.** The official guide has no steps yet.
- **Whether existing password hashes can be imported** into the v2 password component, and which hashing scheme v2 uses.
- **Whether existing sessions survive.** Section 5 gives my inference only.
- **Whether verified email status carries over.**
- **Whether v2 links accounts by email** across password and Google.
- **"Instant session revocation".** The ticket lists it. I found reactive sessions, a server-side check of the token with the deployment, and "sign out of all other devices" in the docs, but no page that describes revocation in those words or how fast it takes effect.
- **GitHub and Apple details, and passkeys in practice.** Read from the docs only; not tried.
- **React Native or Expo support** for anything other than the passkey hooks.
- **Cookie names and session lifetimes in v2**, and whether they differ from v1.
- **Whether the existing variable names can be kept.** The docs show variables declared by the app in `convex/convex.config.ts`, which suggests the current names could be mapped, but I did not test it.
- **The two secondary sources** (the third-party pull request and the GitHub issue) were read through search result summaries, not in full.
- **Nothing was run.** No v2 package was installed and no deployment was touched. All findings come from reading code and documentation.
- **User counts and live session numbers** for either app. I did not query any deployment.
